一、先固定版本、范围和真实运行环境

二、先建立领域地图和项目地图
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

不要直接按文件名字母顺序解释。先回答：

- 项目解决哪些科研问题？用户输入什么，输出什么？
- 输出具有什么统计、数学或科学含义？
- 包含哪些算法家族、检验、模型或组件？
- 各方法依赖哪些假设，适用于什么数据，不适用于什么情况？
- 哪些方法互为替代，哪些组件必须组合？
- 哪些是公共基础设施，哪些是算法特有逻辑？

建立简洁的“问题—方法—假设—输入—输出—适用场景”矩阵。

将项目结构划分为：

1. 用户入口：README、quickstart、tutorial、notebook、CLI、公共 API；
2. 流程编排：主类、参数校验、组件组合、fit/run/predict/estimate 等入口；
3. 公共基础：数据容器、预处理、基类、图结构、统计检验、模型接口和工具；
4. 算法实现：搜索、推断、优化、状态更新、剪枝和终止条件；
5. 验证呈现：tests、benchmark、synthetic data、metrics、plotting 和结果对象。

说明层与层之间的依赖和真实调用关系。

三、先跑通一个最小垂直切片
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

从官方教程、README 或测试中选择一个依赖少、数据小、运行快、理论典型且测试覆盖较好的例子，使其覆盖：

数据构造
→ 公共 API
→ 一个代表算法
→ 一个必要的可插拔组件
→ 结果解释

先运行官方示例，再构造一个可以手算部分结果的微型教学示例。记录入口、参数、调用路径、关键对象、数组或张量 shape、中间状态、输出、随机种子、运行时间与异常。

建立三条经过验证的执行链：

1. 用户调用链：输入 → 公共 API → 参数处理 → 内部算法 → 结果；
2. 数据生命线：原始数据 → 检查/预处理 → 内部表示 → 算法输入 → 输出；
3. 代表算法链：初始化 → 候选/状态 → 核心循环 → 更新/剪枝 → 终止 → 后处理。

调用关系不能只凭函数名推断；尽量通过日志、断点、调用追踪、测试或最小示例验证。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
四、制作源码优先的伴读版本
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

保留原始项目，在独立位置生成 annotated 伴读版；必要时再生成 guided 练习版和 teaching_version 简化实现。

伴读版必须能够沿真实调用顺序连续阅读。理解当前代码所需的信息应放在源码附近，不能只写入 Markdown。Markdown 只负责全局地图、索引、对照表和实验记录；关键内容允许在源码与 Markdown 中重复。

判断是否需要注释的标准不是语法是否复杂，而是普通学习者是否会失去：

- 当前执行阶段；
- 变量、对象和字段的语义；
- 数据来源与去向；
- shape、dtype、值域和索引空间；
- 控制流或对象状态；
- 调用、转换和设计的原因；
- 理论、论文、假设和风险。

采用自适应密度：

- 高密度：数据转换、索引、时间、mask、动态分派、核心算法循环、状态更新、shape 变化、隐藏假设和易误用处；
- 中密度：公共 API、构造器、配置、结果包装、测试、缓存和重要工具函数；
- 低密度：import、日志、路径、明显赋值和重复胶水代码，可用块注释保持流程连续。

不要机械逐行翻译，但主执行链中不能出现关键的“理解断点”。不要用“详情见 Markdown”“这是常规操作”“其余类似”代替必要的就近解释。

使用三层注释：

1. 文件级：所属层次、职责、调用者、依赖、输入输出、阅读顺序；
2. 类/函数级：流程角色、接口契约、数据结构、状态、副作用、假设、异常和扩展点；
3. 代码块/关键行：数据变化、shape、索引、分支、循环、分派、理论原因和风险。

可按需使用标签：

# [流程] [语义] [数据] [形状] [索引] [状态]
# [原因] [理论] [论文] [分派] [假设] [风险]
# [替代] [验证] [下一步]

标签只用于提高定位效率，不要机械堆砌。

五、讲清公共 API、架构和扩展机制
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

对核心公共 API 同时解释两个视角。

用户视角：解决什么问题、最小输入输出、关键参数如何选择、返回对象如何解释、常见误用和不适用条件。

实现视角：调用进入哪个内部函数、参数如何校验和转换、默认组件是什么、基类如何分派、状态保存在哪里、结果怎样组装，以及哪些参数改变算法、哪些只影响日志、输出或性能。

遇到继承、组合、factory、registry、callback 或 strategy 等结构时，不要只说设计模式名称。说明父类提供什么、子类重写什么、运行时实际调用谁，以及新增一种算法或组件需要实现哪些接口和隐含约定。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
六、数据处理是科研方法的一部分
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

即使项目是 pip 库，也不能忽略数据处理。重点解释：

- 用户输入类型和字段语义；
- 样本轴、时间轴、变量轴、节点轴等维度顺序；
- 单数据集和多数据集表示；
- 缺失值、mask、异常值和数据类型转换；
- 排序、对齐、标准化、滞后、窗口和样本选择；
- ID、变量、时间、图和 batch 等索引空间；
- 条件变量、正负样本、邻居或候选构造；
- bootstrap、permutation 和随机采样；
- 缓存和输出矩阵各维的语义。

对关键转换就近说明：转换前的数据结构与 shape、当前操作、数学或工程原因、转换后的 shape/顺序/有效样本数、后续消费者和潜在风险。抽象操作尽量附带 3～5 个变量或时间点的微型例子。

选择一个微型数据集，追踪：

用户输入
→ 数据容器
→ 参数检查
→ 缺失值/mask
→ 时间与变量选择
→ 滞后或窗口样本
→ 统计检验/模型输入
→ 中间量
→ 分数、p 值、图、矩阵或预测结果

每一步解释当前值、shape、dtype、索引空间、有效样本数、丢弃的信息、是否修改原对象以及下一步用途。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
七、讲透代表算法及其论文来源
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

每个代表算法按以下七层理解：

1. Problem：解决什么具体问题；
2. Assumptions：成立需要哪些假设；
3. Input/Output：输入输出的科学含义；
4. Mechanism：核心算法如何推进；
5. Implementation：源码如何实现各步骤；
6. Evidence：测试、仿真或论文如何验证；
7. Alternatives：什么时候应换其他方法。

建立映射：

科研问题
→ 方法假设
→ 数学对象/伪代码
→ 公共 API
→ 源码函数
→ 数据结构和状态
→ 终止条件
→ 输出
→ 测试
→ 论文来源

项目包含很多算法时，先讲透一个代表实现和共享骨架，再解释其他算法相对它改变了什么，不要把所有方法完全重复讲解，也不能只列名称。

为每个重点方法制作简洁的方法卡：问题、假设、核心步骤、公共骨架、特有逻辑、重要参数、复杂度、输出、失败条件、替代方法、来源论文、最小示例和对应测试。

论文仍是理论依据，但不是唯一主线。区分综述、理论基础、原始算法论文和后续扩展；指出论文有但代码没有、代码有但论文未说明、默认参数或实现版本不一致之处。无法确认作者动机时明确标记为推断。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
八、把教程和测试当作可执行规范
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

教程用于理解官方期望的输入、调用顺序、参数组合和结果解释；测试用于理解函数真正保证的契约、边界条件、异常、数值容差和不可随意改变的行为。

为核心功能建立：公共 API → 官方教程 → 对应测试 → 内部实现。

至少选择一个代表测试进行伴读，解释测试情形、输入设计、assertion 保护的性质、错误实现会怎样失败，并补充一个有价值的最小测试。

所有结论区分：

# [官方文档说明] [论文明确说明] [源码静态确认]
# [测试体现的契约] [运行已经验证]
# [根据上下文推断] [目前无法确认]

至少验证：安装/import、官方最小示例、微型教学示例、API 到实现的调用链、关键 shape 和数值范围、代表算法测试、边界输入、错误输入和一个组件替换场景。涉及随机性时记录种子、波动和容差。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
九、通过复写、比较和实验形成能力
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

annotated 版本以连续理解为主，不要每几行插入问题。只在完整数据阶段、公共抽象或核心算法结束后加入少量检查点：输入输出是什么、公共与算法特有逻辑如何区分、依赖哪些假设、替换组件后哪里变化、能否用微型数据手算或测试。

阅读后设计递进任务：

1. 不看教程独立写最小 API 示例；
2. 根据接口复写一个数据转换；
3. 根据伪代码复写一个核心步骤；
4. 实现一个简单、透明的 baseline；
5. 增加一个最小可插拔组件；
6. 添加正常、边界、错误和等价性测试。

形成 research taste 时，不只比较分数。为代表方法记录：科研问题、假设、最简单方案、常见强基线、项目设计、可能收益、额外复杂度、统计与计算代价、证据、失败条件、误用场景和最小对照实验。

比较方法时尽量控制相同数据、预处理、指标、随机条件和计算预算，判断复杂方法的收益是否来自核心设计，而不是额外数据、参数、训练时间或不公平设置。

十、分阶段执行与最终验收
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

按以下顺序推进：

1. 固定版本、建立领域/项目地图并跑通最小示例；
2. 讲清数据容器、预处理、公共 API 和调用链；
3. 制作代表算法及必要公共组件的 annotated 源码；
4. 对齐教程、测试、理论与论文并完成运行验证；
5. 复写核心步骤，加入 baseline、扩展组件和公平比较；
6. 再逐步扩展到其他算法家族。

每阶段说明已完成、已验证、未确认和下一步。不要为了覆盖全仓库而浅尝辄止，也不要只讲一个函数便声称掌握项目。项目过大时分批继续，不能用 Markdown 概述代替源码伴读。

保留 original、annotated、guided、可选 teaching_version，以及 experiments。不要覆盖上游源码，不擅自修复 bug、改变公共 API、默认参数、数据顺序、随机性或算法语义。发现问题先记录证据；每阶段运行相关测试。

最终应形成：

- 固定版本与环境记录；
- 科研问题和方法地图；
- 项目分层与三条执行链；
- 最小官方示例和微型教学示例；
- annotated 伴读源码；
- 数据生命线和 API—实现映射；
- 代表算法的方法卡及理论/论文映射；
- 教程—测试—实现映射与新增测试；
- 核心步骤复写、简单 baseline 和比较实验；
- 已验证事实、未确认推断及学习范围记录。

最终验收不看注释数量或浏览文件数量，而看我能否：

1. 解释项目覆盖的问题、方法和假设；
2. 根据数据与研究目标选择方法；
3. 独立写出最小调用例子；
4. 从公共 API 追踪到真实实现；
5. 解释数据怎样变成算法输入和科学输出；
6. 区分公共框架与算法特有逻辑；
7. 通过运行和测试验证理解；
8. 复写一个简化核心步骤；
9. 增加一个小型扩展组件；
10. 公平比较两种方法并说明取舍；
11. 用该工具箱完成一个小型研究问题。

真正的完成标准是：我不仅能使用这个库，而且能够理解其数据、架构、算法、假设和证据，并有能力独立验证、修改和判断它。
